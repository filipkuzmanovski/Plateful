# Plateful AI features: handoff brief

Written 2026-10-29 for a new Claude Code session. Read this whole file before doing anything. Then start with the **superpowers:brainstorming** skill: this is architectural work, so it goes questions, then approaches, then a written spec, then a plan, then subagent-driven build, then review, per sub-project.

## 1. What the user wants

The user is a student, and Plateful is a portfolio and university project. Together with their professor, they want to add AI features to the existing Plateful app. The deadline is **February 2027**.

### The features
1. **Ingredients to recipe.** The user types the ingredients they have, and the app generates a recipe based on recipe data it knows.
2. **Photo to recipe.** The user photographs their fridge, pantry or kitchen. The app recognises the food and generates a recipe from it.
3. **Three daily meals.** When the site loads, the user gets a breakfast, lunch and dinner suggestion. These are based on food likes and dislikes chosen at sign-up. They're newly generated as well; see "Generation, not retrieval".
4. **Instagram food blogs.** The professor's idea, reshaped into two legitimate options. The user wants **both**:
   - **Paste import:** a user pastes an Instagram post's caption, or uploads a screenshot of it. The AI turns it into a structured recipe, which pre-fills the normal "New recipe" form. It then goes through the existing admin review.
   - **Blogger connect:** a food blogger connects their own Instagram professional account (Business or Creator) through Meta's "Instagram API with Instagram Login" and opts in. Plateful imports their posts as draft recipes.

   Reading the feeds of accounts a user *follows* is **not possible**. Meta shut down personal-account API access (Basic Display API) in December 2024, and scraping breaks Meta's terms. Don't revisit this.

### Generation, not retrieval (the user's explicit requirement)
The AI must **create new, original recipes** for the user. It must not look up and reprint a recipe that already exists in the database or dataset.

- **What the recipe data is for:** inspiration and grounding. It supplies:
  - which ingredients go together, and typical flavour pairings per cuisine;
  - sensible proportions, cooking techniques, temperatures and times;
  - the steps and structure a good recipe has.

  It is never the answer itself.
- **Prompting:**
  - Give the model a few *example* recipes as reference.
  - State clearly that it must invent a new dish: its own name, its own combination, its own method.
  - Keep some randomness, so asking twice with the same ingredients gives different recipes.
- **Novelty check, enforced in code:**
  - After generating, compare the result against the closest dataset and Plateful recipes, by ingredient overlap (for example Jaccard similarity on normalised ingredient names) and title similarity.
  - If it's too close to an existing recipe, ask the model again for something more different.
  - Pick and record the threshold during design; show it in the tests.
- **Saving and labelling:**
  - Generated recipes are stored as new recipes owned by the requesting user, `source = 'ai'` (a new value; needs a migration).
  - They carry the "Generated by AI" label.
  - Keep a "Generate another" button.

### Decisions already made (don't re-ask)
| Question | Decision |
|---|---|
| Train our own model, or use an existing AI? | An existing AI is fine. There's no requirement to train a model. |
| Budget | **Free.** No paid AI usage. |
| Where it lives | **Inside Plateful**, in the same repo and app. Not a separate project. |
| Instagram | Both options above. Blogger connect is the riskiest; build it last. |

**Why inside Plateful rather than a separate project:** it's faster. Sign-in, 2FA, admin review, recipes, storage, the UI system, tests and deployment already exist. A separate project would rebuild all of that. With an existing AI reached over HTTP, there's no need for a separate Python ML service; the Spring Boot backend can call the AI provider directly.

## 2. Hard constraints for the design

- **Free tier only.** Free tiers have per-minute and per-day request limits.
  - Design for that: rate-limit AI calls per user, cache results, and degrade gracefully with a clear message when the daily quota is used up.
  - **Feature 3 must not call the AI on every page load.** The daily meals are generated too, under the same "create, don't reprint" rule:
    - generate one breakfast, lunch and dinner per user **once per day**, on their first visit that day;
    - store them, and serve the stored set on every later load;
    - if the free quota is used up, fall back to picking matching recipes from the database, with a note that today's suggestions aren't freshly generated.
  - Default suggested here; the user can still choose database picks only, to save quota.
- **The AI key lives only on the backend,** in an environment variable such as `AI_API_KEY` set in the IntelliJ run configuration. Never put it in the frontend, never commit it, never print it.
- **Keep the provider swappable.** Put the AI provider behind a small Java interface, so changing provider is configuration, not a rewrite. If the free tier ever proves too limited, the cheapest paid option known on 2026-10-29 is Claude Haiku 5.5: $0.10 per million input tokens and $0.50 per million output tokens, image input supported. It isn't free, so the user must approve it first.
- **Allergies and dislikes are hard filters enforced in code** (SQL or Java), never only by the prompt. Generated recipes must not contain excluded ingredients; validate the output and retry or reject.
- **Generated recipes carry a visible label.** For example: "Generated by AI. Not checked by a person. Use your judgement, especially with meat, eggs and allergens."
- **Fridge photos are personal data.** Recommended: send them to the AI and don't store them. Update the Privacy Policy (`recipe-app-frontend/src/features/content/PrivacyPage.tsx`) to name the AI provider and explain what's sent. The provider's free tier may use inputs to improve its products; check this and disclose it.
- **No emojis** anywhere in the UI. Tests call `expectNoEmoji()`.
- **Publishing:** anything that becomes a public recipe (Instagram imports, or a generated recipe the user chooses to publish) goes through the existing admin review queue.

## 4. Suggested shape (starting point for brainstorming, not a decision)

Split into sub-projects. Each gets its own spec, plan, build, review and merge, in this order:

1. **Food preferences and the dataset. No AI yet.**
   - Add a preferences step to sign-up, after the existing profile step: likes, dislikes, allergies, and diet (vegetarian, vegan, gluten-free, dairy-free). Store it in a new table.
   - Import the recipe dataset subset, to use as reference material, with a meal-type signal (breakfast, lunch, dinner) inferred at import. Decide whether dataset recipes are publicly browsable or only used behind the scenes.
   - Build the database picker for the daily meals: filter out allergens and dislikes, score by likes, cuisines, diet flags, ratings and saves. It is feature 3's fallback, and it shows something before the AI exists.
   - This has no external dependency, so start here.
2. **AI provider and ingredients to new recipe (feature 1).**
   - The provider interface, configuration, per-user rate limiting and the error states.
   - The flow:
     1. find reference recipes by ingredient overlap in Postgres;
     2. ask the AI to invent a **new** recipe inspired by them, in structured JSON;
     3. validate the result, run the allergy filter and the novelty check (section 1), and regenerate if it fails.
   - Show it with the AI label. Offer "Generate another", "Save" (private) and "Publish" (goes to admin review).
   - Then switch the daily meals to generated: once per user per day, stored, falling back to the database picker.
3. **Photo to recipe (feature 2).**
   - A vision call returns an ingredient list.
   - The user **confirms and edits** the list, then it reuses feature 1's flow. Don't store the photo.
4. **Instagram paste import (option A).**
   - Caption text or screenshot to a structured recipe, pre-filling the existing `RecipeFormPage`.
   - Then the normal create, pending and admin-review path.
5. **Instagram blogger connect (option B).** Last, because Meta setup is the main risk.
   - Meta app, Instagram Login OAuth, tokens stored encrypted and server-side only.
   - Import a connected blogger's posts as drafts that they review and submit.

**Rough timeline:** about 5 to 8 weeks of part-time work for sub-projects 1 to 4. Sub-project 5 adds 1 to 3 weeks, depending on Meta. That fits before February with room for deployment, which is still pending.

- **Other tables:** `recipe_photos` (V3), `recipe_ratings`, `recipe_comments`, `comment_reactions`, `saved_recipes` (V4).
- RLS is on for every public table. The backend connects as the table owner.

### Rules already in place
- **Visibility:**
  - `service/RecipeVisibility` is the one place that decides who sees a recipe: approved, or the author, or an admin at aal2.
  - Browse and search show approved recipes only.
  - Search is the `q` parameter: per word, matching the title or an ingredient name.
- **Sign-in:**
  - Supabase Auth with optional TOTP 2FA. The backend checks the JWT (ES256).
  - `@CurrentUserId` and `@OptionalCurrentUserId` resolve the user.
  - `MfaEnforcementFilter` requires aal2 on writes, `/me` and `/admin` paths when the user has a factor.
- **Admin:**
  - `/api/admin/**` sits behind `AdminGuardInterceptor`: admin queue, approve and reject, remove recipe or comment with a reason.
  - Emails go through Gmail SMTP (`MAIL_USERNAME`, `MAIL_PASSWORD` in the run configuration), sent after commit and in the background.
- **Storage:**
  - Supabase buckets `recipe-photos` and `recipe-videos`, uploaded straight from the browser into `{userId}/...`.
  - The bucket SQL is in `docs/supabase/` and is run by hand by the user.
  - `public.is_admin()` exists as a security-definer function.
- **Frontend sign-in state:** `useAuth()` gives a `status` of loading, anonymous, needs-profile, needs-mfa or ready, plus `profile: MyProfile` with `isAdmin` and `rejectedCount`.
- **Sign-up flow:**
  1. The `SignupPage` collects the birth date (13+ check) and calls Supabase sign-up.
  2. `CompleteProfilePage` posts the names to `/api/users/me`.

  A preferences step would naturally follow this.

## 6. Safety rules and commands (binding)

### Before any backend compile
Run this check, because a stale launch configuration once wiped imported recipes twice:

```
powershell -NoProfile -Command "Get-CimInstance Win32_Process -Filter \"Name='java.exe'\" | Where-Object { \$_.CommandLine -match 'RecipeAppBackendApplication' } | ForEach-Object { \$_.CommandLine -match 'spoonacular' }"
```

If it prints `True`, stop.

### Running backend tests
- Set `export JAVA_HOME="$USERPROFILE/.jdks/ms-21.0.9"`, then run `./mvnw -q test -Dtest=<Classes>` from `RecipeAppBackend/`.
- **Never run it unfiltered.** The context-load test needs the live database.
- Read the counts from `target/surefire-reports` after clearing it first.

### Database tests
- Use exactly the annotations of `RecipeCuisineQueryDbTest`, and write only inside the rolled-back `@DataJpaTest` transaction.
- Export the password without printing it, from `RecipeAppBackend/`:

  ```
  export SUPABASE_DB_PASSWORD="$(python -c "import re;s=open('.idea/workspace.xml',encoding='utf-8').read();m=re.search(r'name=\"SUPABASE_DB_PASSWORD\" value=\"([^\"]*)\"',s);print(m.group(1) if m else '')")"
  ```

### Migrations
- Flyway is disabled in DbTests. A new migration reaches the live database only when the user's running backend restarts after a compile.
- Never apply migration SQL by hand.
- Mapping a SMALLINT column needs `@JdbcTypeCode(SqlTypes.SMALLINT)`. Hibernate's `ddl-auto=validate` fails startup otherwise.

### Frontend
Run through the Bash tool from `recipe-app-frontend/`: `npx vitest run` and `npm run build` must both be green before each commit.

### Never
- print secrets;
- edit `.idea/`;
- enter credentials into sign-in pages;
- run destructive data operations without the user's explicit yes.
