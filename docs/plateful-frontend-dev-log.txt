================================================================================
 PLATEFUL FRONTEND — DEVELOPMENT LOG
================================================================================

What this file is
-----------------
A task-by-task record of how the Plateful frontend (recipe-app-frontend/) was
built: what each task delivered, how it was done, and explanations of the key
code. It follows the implementation plan in
docs/superpowers/plans/2026-07-14-plateful-frontend.md, which was derived from
the design spec docs/superpowers/specs/2026-07-14-frontend-design.md.

Each task was built test-first (write a failing test, make it pass, commit),
then checked by an independent reviewer before the next task started. Fixes
that came out of a review are logged as their own entries.

File paths below are relative to recipe-app-frontend/ unless they start with
docs/ or RecipeAppBackend/.


--------------------------------------------------------------------------------
 THE BIG PICTURE (read this first)
--------------------------------------------------------------------------------

Plateful is a single-page app (SPA): the browser downloads one JavaScript
bundle, and from then on React swaps "pages" in and out without full reloads.
All recipe data lives in the Spring Boot backend (RecipeAppBackend/), which the
frontend calls over HTTP at http://localhost:8080/api/... .

Request flow for, say, opening the browse page:

  Browser URL (/?cuisine=thai)
     -> React Router picks the page component (BrowsePage)
     -> TanStack Query asks "do I already have this data cached?"
     -> if not, calls browseRecipes() in src/api/recipes.ts
     -> which calls the shared fetch wrapper in src/api/client.ts
     -> which adds the login token and calls the Spring API
     -> JSON comes back, typed as Page<RecipeDisplay> (src/lib/types.ts)
     -> React renders RecipeCard components from it

Login works differently: Supabase (a hosted auth service) handles sign-up and
sign-in and gives the browser a JWT (a signed token proving who you are). The
frontend never reads recipe data from Supabase — it only borrows the token and
attaches it to calls to our own API, where Spring verifies it.

Tech stack, and what each piece is for:

  Vite 8              Dev server + production bundler (npm run dev / build)
  React 19            UI components
  TypeScript 6        Types, in strict mode so mistakes fail at compile time
  React Router 8      Maps URLs to page components
  TanStack Query 5    Fetches, caches and refreshes server data
  supabase-js 2       Sign-up / sign-in / session only
  Tailwind CSS 4      Styling via utility classes, themed to our tokens
  react-hook-form +   Form state and validation (used by the recipe form)
    zod 4
  Radix Dialog        Accessible confirm dialogs
  sonner              Toast notifications
  Vitest 4 + Testing  Test runner, React rendering in tests, and MSW, which
    Library + MSW 2   fakes the backend at the HTTP level

Visual direction ("Fresh Editorial", picked from mockups): near-black text on
white, one green accent, thin gray hairlines, square corners, Inter font, and
photography as the only real color.

 TASK 1 — Scaffold, theme, test infrastructure
 Commits on main: 363fe69 (scaffold), 3fef2b2 (review fix: TypeScript strict)
================================================================================

What was built
--------------
An empty but fully wired project: Vite + React + TypeScript, the Tailwind
theme, a handful of shared UI building blocks, and the testing setup that
every later task relies on.

How it was done
---------------
1. `npm create vite@latest recipe-app-frontend -- --template react-ts`
   generated the skeleton. All libraries were installed in two npm commands
   (runtime dependencies, then dev/test-only ones). The template's demo files
   (App.css, logos) were deleted.

2. vite.config.ts — three jobs in one file:
     plugins: [react(), tailwindcss()]
       React support, and Tailwind compiled at build time (Tailwind v4 is a
       Vite plugin, with no separate config file).
     resolve.alias: { '@': path.resolve(__dirname, 'src') }
       Lets code write `import { api } from '@/api/client'` instead of
       fragile relative paths like '../../api/client'.
     test: { environment: 'jsdom', globals: true, setupFiles: ... }
       Configures Vitest. jsdom is a fake browser DOM so React components
       can render inside Node. `globals: true` makes test(), expect() and
       vi available without imports.

   tsconfig.app.json mirrors the alias ("paths": {"@/*": ["./src/*"]}) so
   TypeScript understands '@/...' too. Vite and TypeScript resolve imports
   independently, so the alias must be declared in both.

3. src/index.css — the whole design system lives here:

     @import 'tailwindcss';
     @import '@fontsource-variable/inter';    <- self-hosted font, no CDN
     @theme {
       --font-sans: 'Inter Variable', system-ui, sans-serif;
       --color-ink: #111111;
       --color-accent: #16a34a;
       --color-hairline: #e5e5e5;
       --color-muted: #737373;
     }

   Tailwind v4 turns every `--color-x` in @theme into utility classes, so
   `--color-accent` makes `text-accent`, `bg-accent`, `border-accent` and so
   on available everywhere. Changing a token here re-skins the whole app.

4. src/components/ui.tsx — small shared components:
     Button          variant = 'primary' | 'outline' | 'danger'. A lookup
                     object maps each variant to its classes, and the rest
                     of the props are spread onto a real <button> so
                     onClick, disabled, type etc. all just work.
     Field           A <label> wrapping an uppercase caption + the input +
                     an optional error line with role="alert" (so screen
                     readers announce validation errors).
     TextInput       A styled <input>.
     SectionHeading  The uppercase, letter-spaced heading with a 2px black
                     rule underneath (INGREDIENTS, INSTRUCTIONS, ...).
     Spinner         A "Loading…" line with role="status".

5. Test infrastructure:
     src/test/server.ts  `export const server = setupServer();`
       An MSW server. Tests register fake API responses on it with
       server.use(http.get(url, handler)). MSW intercepts fetch() itself,
       so our real API client code runs end-to-end in tests.
     src/test/setup.ts   Runs before every test file: starts the MSW
       server, resets handlers after each test (so tests can't leak fakes
       into each other), and adds jest-dom matchers like
       toBeInTheDocument().

6. .env.example documents the three environment variables
   (VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, VITE_API_BASE_URL). The real
   values go in .env.local, which git ignores. Vite only exposes variables
   prefixed VITE_ to browser code, and inlines them at build time.

Review fix (3fef2b2)
--------------------
The reviewer noticed the newer Vite template had shipped without
`"strict": true` in tsconfig.app.json. Strict mode turns on null checking
(a value typed `string | null` must be checked before use) and bans implicit
`any`. Every later task depends on it to catch bugs at compile time, so it was
enabled before anything else was built on top.

How it was tested
-----------------
One smoke test rendered the app and checked the PLATEFUL wordmark appeared,
proving React, Vitest, jsdom and the setup file were all wired together. It
was deleted in Task 3 once real tests existed.

 TASK 2 — Types, API client, resource modules
 Commit on main: 45828e7
================================================================================

What was built
--------------
The entire data layer: TypeScript types mirroring the backend's JSON, one
fetch wrapper that every API call goes through, and one small module per
backend resource.

How it was done
---------------
1. src/lib/types.ts — interfaces copied field-for-field from the Spring DTOs
   (RecipeDisplayDto, RecipeCommentDisplayDto, ...). Examples:

     interface RecipeDisplay { id: string; title: string;
       readyInMinutes: number | null; ... 28 fields total }
     interface Page<T> { content: T[];
       page: { size; number; totalElements; totalPages } }

   Java Integer/BigDecimal fields that can be null become `number | null`,
   so strict TypeScript forces the UI to handle "no value" (e.g. a recipe
   with no cooking time). Page<T> is a generic: Page<RecipeDisplay>,
   Page<CommentDisplay> and so on all share one definition, matching the
   backend's paginated response shape.

2. src/auth/supabaseClient.ts creates the one Supabase client for the app,
   reading the URL and key from env vars. The comment marks it as auth-only.

3. src/api/client.ts — the heart of the data layer. Walkthrough:

     export class ApiError extends Error {
       status: number; detail: string; errors?: Record<string, string>;
       ...
     }
   A typed error. The backend returns failures as RFC 9457 "ProblemDetail"
   JSON: { status, detail, errors? }. Turning that into an ApiError lets UI
   code write `if (e instanceof ApiError && e.status === 404)` and lets
   forms map `errors.title` onto the title field. (The fields are declared
   explicitly instead of with TypeScript's constructor shorthand because the
   project's `erasableSyntaxOnly` setting forbids that shorthand.)

     async function request(path, init) {
       const headers = new Headers(init.headers);
       if (init.body) headers.set('Content-Type', 'application/json');
       const { data } = await supabase.auth.getSession();
       const token = data.session?.access_token;
       if (token) headers.set('Authorization', `Bearer ${token}`);
   Attaches the login token only when someone is logged in. Anonymous
   visitors send no header, which the backend allows for public GETs.

       const res = await fetch(`${BASE}${path}`, { ...init, headers });
       if (res.ok) return res;
       if (res.status === 401) await supabase.auth.signOut();
   A 401 means the token expired or is invalid. Signing out clears the
   session; the auth provider (Task 3) notices and the UI goes back to the
   logged-out state.

       const problem = await res.json().catch(() => null);
       throw new ApiError(res.status, problem?.detail ?? `Request failed...`,
                          problem?.errors);
   Some errors (e.g. Spring Security's 401) have an empty body, so a JSON
   parse failure falls back to a generic message instead of crashing.

   Two exported wrappers: api<T>() returns parsed JSON typed as T, and
   apiVoid() is for endpoints that answer 204 No Content.

4. Resource modules — src/api/recipes.ts, users.ts, ratings.ts,
   comments.ts, reactions.ts. These are the ONLY places URLs appear, so if
   an endpoint moves, one line changes. Two worth explaining:

     browseRecipes(filter, page):
       for (const [key, value] of Object.entries(filter)) {
         if (value !== undefined && value !== null && value !== '')
           params.set(key, String(value));
       }
   Unset filters are left OUT of the query string entirely. Sending
   vegan=false would ask the backend for non-vegan recipes, which is not
   the same as "don't filter on vegan". Page size is fixed at 12 via the
   exported PAGE_SIZE constant.

     getMyRating(recipeId):
       try { return (await api(...)).rating; }
       catch (e) { if (e instanceof ApiError && e.status === 404) return null;
                   throw e; }
   The backend answers 404 when you haven't rated a recipe. That isn't an
   error for the UI, it just means "no rating", so it becomes null. Every
   other failure is re-thrown.

5. src/test/fixtures.ts — builder functions for test data (recipeFixture,
   commentFixture, pageOf, profileFixture). recipeFixture({ title: 'X' })
   returns a complete, realistic recipe with just the title overridden, so
   tests only spell out what they care about.

How it was tested
-----------------
src/api/client.test.ts (4 tests, all through MSW):
  - JSON parses, and no Authorization header is sent when logged out
  - A ProblemDetail 400 becomes an ApiError with status, detail and errors
  - browseRecipes sends cuisine/vegan/page/size but omits unset filters
  - getMyRating turns a 404 into null

 TASK 3 — Auth provider, provisioning, routing shell
 Commit on main: 934e653
================================================================================

What was built
--------------
Login and signup pages, the "complete your profile" step, the app header,
route protection, and the full route table (later pages started as
placeholders and are swapped in task by task).

How it was done
---------------
1. The provisioning problem. Supabase knows a user's email and password, but
   our database also needs a profile row with first and last name. The
   backend contract: after login, GET /api/users/me returns the profile, or
   404 if it doesn't exist yet. Then POST /api/users/me {firstName,
   lastName} creates it (safe to repeat).

2. src/auth/AuthProvider.tsx — a React Context that tracks login state for
   the whole app as a small state machine:

     'loading'        still finding out who you are
     'anonymous'      not logged in
     'needs-profile'  logged in, but no profile row yet
     'ready'          logged in with a profile

   On mount it reads the current session (supabase.auth.getSession()) and
   subscribes to changes (supabase.auth.onAuthStateChange()). Whenever the
   session changes, resolveProfile() calls GET /api/users/me: 200 sets the
   profile and 'ready', and 404 sets 'needs-profile'. Components read all of
   this with the useAuth() hook. (Task 3 Fix below hardens this logic.)

   Context is used so any component — the header, the rating box, the
   comment form — can ask "who is logged in?" without the state being passed
   down through every component in between.

3. src/auth/ProtectedRoute.tsx — wraps pages that need a login:
     loading        -> spinner
     anonymous      -> <Navigate to="/login" state={{ from: path }} />
                       (login sends you back to where you were going)
     needs-profile  -> <Navigate to="/complete-profile" />
   The needs-profile redirect is skipped when you're already ON
   /complete-profile. Without that check the page would redirect to itself
   forever.

4. Pages:
     LoginPage / SignupPage  Call supabase.auth.signInWithPassword /
                             signUp and show Supabase's error message on
                             failure.
     CompleteProfilePage     Collects first/last name, calls createMe(),
                             hands the new profile to the context via
                             setProfile(), and navigates to /me.

5. src/components/AppShell.tsx — the layout around every page: the PLATEFUL
   wordmark, nav links (Browse, plus New Recipe only when 'ready'), a user
   menu (My profile / Sign out) or a Sign in link, an ErrorBoundary around
   the page content, and the toast container.

   src/components/ErrorBoundary.tsx is a class component (React still only
   offers error boundaries as classes). If a page throws while rendering,
   it shows a friendly message instead of a blank white screen.

6. src/AppRoutes.tsx — the route table, final from day one:
     /                    BrowsePage          public
     /recipes/new         RecipeFormPage      protected
     /recipes/:id         RecipeDetailPage    public
     /recipes/:id/edit    RecipeFormPage      protected
     /users/:id           PublicProfilePage   public
     /me                  MyProfilePage       protected
     /login, /signup      auth pages          public
     /complete-profile    CompleteProfilePage protected
   All routes nest under AppShell (React Router's <Outlet/> marks where the
   page renders inside the layout).

7. src/App.tsx stacks the providers: QueryClientProvider (data cache) >
   AuthProvider (who's logged in) > BrowserRouter (URLs) > AppRoutes. The
   QueryClient retries failed requests twice and treats data as fresh for
   30 seconds.

8. src/test/utils.tsx — renderApp('/some/route') renders the WHOLE app with
   a MemoryRouter (an in-memory URL, so no real browser address bar is
   needed) and a fresh cache with retries off, so tests are fast and
   isolated.

How it was tested
-----------------
src/auth/auth.test.tsx replaces the Supabase client with a fake that reports
a logged-in session (vi.mock), while the backend is faked with MSW:
  - A logged-in user with no profile who opens /me is redirected to
    /complete-profile. After typing a name and saving, they land on /me
    showing "Jane Doe", and the POST body is verified.
  - A user with a profile sees their name in the header.

 TASK 3 FIX — Hardening the auth state machine
 Commits on feature/frontend-pages: 8c9d049, a6a0216
================================================================================

Why
---
The reviewer found gaps in the AuthProvider logic as originally planned:

  1. If supabase.auth.getSession() ever failed, nothing caught the error,
     and the app would sit on 'loading' forever: every protected page shows
     an endless spinner.
  2. Supabase v2 fires an INITIAL_SESSION event through onAuthStateChange at
     the same moment getSession() resolves, so GET /api/users/me was fetched
     twice on every page load. Token refreshes (about hourly) fetched it
     again.
  3. (Found on the second review.) A brief network failure while loading the
     profile left a logged-in user looking logged out, with no retry. And a
     slow profile response for a previous user could arrive late and
     overwrite the current user's state.

How it was fixed (src/auth/AuthProvider.tsx)
--------------------------------------------
Three variables live inside the useEffect, so each mount gets fresh ones:

  let cancelled = false;
     Set by the cleanup function. Responses that arrive after the component
     unmounted are ignored. (React StrictMode mounts, unmounts and re-mounts
     every component in development, so this happens on every page load in
     dev.)

  let lastUserKey: string | null | undefined;
     The user id the state was last resolved for (null = logged out,
     undefined = nothing resolved yet). The first line of resolveProfile:

       const key = s?.user?.id ?? null;
       if (key === lastUserKey) return;

     If the event is about the same user we already resolved (the
     INITIAL_SESSION double-fire, a token refresh), there's nothing to do.
     That fixes gap 2. A different user or a sign-out has a different key,
     so it still re-resolves.

  let latest = 0;
     A counter bumped on every real resolution:

       const run = ++latest;
       const isCurrent = () => !cancelled && run === latest;

     Each resolution remembers its own number. When its HTTP response comes
     back it only applies the result if no newer resolution has started.
     So a slow response for user A can never overwrite user B. That fixes
     the stale half of gap 3.

The error path:

  } else {
    lastUserKey = undefined; // transient failure: let the next auth event retry
    setStatus('anonymous');
  }

On a non-404 failure the remembered key is cleared, so the next auth event
for that same user is no longer treated as a duplicate and the profile load
is retried. That fixes the retry half of gap 3.

The getSession failure (gap 1) now has a .catch() that falls back to
'anonymous'. But it only does so if `lastUserKey === undefined`, so a late
failure can't overwrite a state that an auth event already resolved.

How it was tested
-----------------
src/auth/auth-events.test.tsx. The fake Supabase client captures the
onAuthStateChange callback, so tests can fire auth events by hand:
  - SIGNED_IN fetches the profile once. A following TOKEN_REFRESHED for the
    same user does NOT fetch again (counts real HTTP calls through MSW).
  - getSession rejecting lands on 'anonymous' (the Sign in link appears)
    rather than an endless spinner.
  - Sign-in as user 1, sign-out, sign-in as user 2: two fetches, and the
    header shows user 2.
  - First profile fetch fails with a 500; the next event retries and
    succeeds.
The 500 case was written first and failed before the fix (only one fetch
happened), proving the test actually detects the bug.

 TASK 4 — Browse page
 Commit on feature/frontend-pages: 7a742a3
================================================================================

What was built
--------------
The home page: a filter bar on top, a responsive grid of recipe cards, and
page-number pagination. Filters live in the URL.

How it was done
---------------
1. Why the URL holds the filters. Instead of keeping filter choices in React
   state, they are stored in the query string:
     /?cuisine=thai&vegan=true&page=1
   That gives three things for free: filtered views can be shared or
   bookmarked, the browser Back button undoes a filter change, and a page
   refresh keeps your filters.

2. src/features/browse/BrowsePage.tsx

     const [params, setParams] = useSearchParams();
   React Router's hook for reading and writing the query string.

     function readFilters(params): FilterValues { ... }
   Turns URL strings into typed values: vegan is true only when the URL
   says exactly "true", and missing values become '' / false.

     function toApiFilter(v): RecipeFilter {
       return { cuisine: v.cuisine || undefined,
                vegan: v.vegan || undefined, ... }
   `x || undefined` turns '' and false into undefined, which browseRecipes()
   then leaves out of the request. (As in Task 2: "not filtering" must never
   be sent as "false".)

     useQuery({
       queryKey: ['recipes', params.toString()],
       queryFn: () => browseRecipes(toApiFilter(values), page),
     })
   TanStack Query caches results under the key. Because the key is the
   whole query string, every filter combination is cached separately.
   Switching back to a filter you used a moment ago is instant. (The polish
   pass later added keepPreviousData, which keeps the previous grid visible,
   dimmed and marked busy, while the new results load. See "Final review
   fixes" at the end.)

     function patchParams(patch) {
       ... set or delete each changed key ...
       next.delete('page');   // filter change resets pagination
       setParams(next);
     }
   Writing the URL is the only thing a filter click does. React Router
   re-renders, the query key changes, and TanStack Query fetches. Changing a
   filter drops the page number, because page 3 of the old results means
   nothing for the new filter.

   The page then renders one of four states: loading spinner, error with a
   Retry button (query.refetch()), "No recipes match" with Clear filters,
   or the grid + pagination.

3. src/features/browse/FilterBar.tsx — a "controlled" component: it owns no
   state. It receives the current values and calls onChange with a patch.
   Contents: a cuisine <select> over the exported CUISINES list (the 10
   cuisines seeded from Spoonacular), four diet toggle buttons (filled black
   when active), and max-time and min-rating selects. Each select has an
   aria-label, so it's accessible and tests can find it by name.

4. src/components/RecipeCard.tsx — a <Link> to /recipes/:id containing the
   photo (or a 🍽 placeholder when there's none), title (turns green on
   hover via Tailwind's `group-hover:`), StarDisplay, ready time, and
   cuisines. Shared with the profile pages in Task 8.

   src/components/StarDisplay.tsx shows "★ 4.6 (28)", or "No ratings yet"
   when the average is null.

   src/components/Pagination.tsx renders one button per page from the
   backend's totalPages. The current page is filled black and marked
   aria-current="page". It renders nothing when there's only one page.

5. Responsive grid: `grid-cols-1 sm:grid-cols-2 lg:grid-cols-4` gives one
   column on phones, two on tablets and four on desktops (Tailwind's
   breakpoint prefixes apply from that width up).

How it was tested
-----------------
src/features/browse/browse.test.tsx (5 tests). MSW captures the actual
request URL, so the tests assert what is really sent to the backend:
  - Cards render title, rating and time from the API response
  - Choosing cuisine=italian and clicking Vegan sends cuisine=italian,
    vegan=true and page=0
  - Opening /?cuisine=thai&maxReadyInMinutes=30&page=1 sends those exact
    params, so URL to request works
  - An empty result shows the empty state
  - totalPages: 3 renders a "Go to page 3" button
All 5 failed before the page existed. After implementing: 15/15 tests
passing.

 TASK 5 — Recipe detail page + rating box
 Commit on feature/frontend-pages: ac911fc
================================================================================

What was built
--------------
The page at /recipes/:id, in the two-column layout chosen from the mockups:
a "facts card" on the left that stays pinned while you scroll, and the
recipe content on the right. The left card holds your own star rating.

How it was done
---------------
1. src/features/recipe/RecipeDetailPage.tsx

     const { id } = useParams<{ id: string }>();
     const query = useQuery({ queryKey: ['recipe', id],
                              queryFn: () => getRecipe(id!), retry: false });
   useParams reads the :id from the URL. retry: false because a 404 (bad
   recipe id) will never succeed on retry, so it should fail fast. The
   error branch checks
     query.error instanceof ApiError && query.error.status === 404
   to show "Recipe not found." instead of a generic error. This is where
   the typed ApiError from Task 2 pays off.

   Layout:
     <div className="flex flex-col gap-8 lg:flex-row">
       <aside className="lg:w-2/5"> <div className="lg:sticky lg:top-4"> ...
       <article className="flex-1"> ...
   Below the `lg` breakpoint everything stacks vertically (facts card
   first). On large screens it becomes a row, and `sticky top-4` keeps the
   facts card in view while the instructions and comments scroll.

   Left card:
     - photo, or a 🍽 placeholder when the recipe has none
     - ready / cook time and servings, each shown only when not null (this
       is where the `number | null` types force a check)
     - diet badges built by DietBadges: an array of
       `recipe.vegan && 'Vegan'` etc. filtered to the truthy entries
     - calories / protein / fat / carbs, shown only when calories exist
       (imported recipes have them; hand-written ones usually don't)
     - the RatingBox

   Right column:
     - title and StarDisplay (the average)
     - attribution: user recipes link to the author's profile
       ("by Jane Doe" -> /users/:id); imported recipes link out to the
       original site ("From Pink When ↗", target="_blank"
       rel="noreferrer", so the other site can't control our tab)
     - ingredients as a checklist. The checkboxes are purely visual and
       nothing is saved; they help while cooking.
     - instructions: the numbered structured steps when the recipe has
       them, else the raw instructions text (whitespace-pre-line keeps its
       line breaks), else "No instructions provided"
     - the comments heading and a CommentsSlot placeholder (Task 6)

2. src/features/recipe/RatingBox.tsx

     const myRating = useQuery({ queryKey: ['myRating', recipeId],
                                 queryFn: () => getMyRating(recipeId),
                                 enabled: status === 'ready' });
   `enabled` stops the query from running for anonymous visitors, who have
   no rating to fetch.

     const rate   = useMutation({ mutationFn: (n) => putMyRating(recipeId, n),
                                  onSuccess: invalidate });
     const unrate = useMutation({ mutationFn: () => deleteMyRating(recipeId),
                                  onSuccess: invalidate });
   useMutation is TanStack Query's tool for writes. On success, invalidate()
   marks three cached queries as stale so they refetch: your rating, this
   recipe (its average changed), and every browse list (the cards show
   averages too).

     onClick={() => (current === n ? unrate.mutate() : rate.mutate(n))}
   Clicking a different star rates; clicking the star you already gave
   removes your rating. That is the backend's DELETE .../ratings/me.

   Each star is a <button> with aria-label="Rate 4 stars" and
   aria-pressed={current === n}. The label lets screen readers (and tests)
   identify each star, and aria-pressed announces which one is selected.

   Deviation from the plan, made by the implementer and confirmed by test:
     if (myRating.isPending) return <p>Loading your rating…</p>;
   The planned code drew the stars immediately while your saved rating was
   still loading. That had a real bug: clicking your current star before
   the load finished would send "rate 4" again instead of "remove rating",
   because the component didn't know yet that 4 was your rating. The stars
   now appear only once your rating is known. If loading the rating fails,
   isPending becomes false and the stars render unselected, so the box
   can't get stuck.

How it was tested
-----------------
src/features/recipe/detail.test.tsx (4 tests). The Supabase client is faked
as logged in, and MSW serves the recipe, comments and rating:
  - The title, an ingredient, a structured step, the Gluten free badge,
    calories and the "From Pink When" attribution all render
  - With a saved rating of 4, the 4th star is aria-pressed, and clicking it
    sends DELETE (un-rate)

 TASK 6 — Comments, reactions, and the confirm dialog
 Commit on feature/frontend-pages: b0ff27b
================================================================================

What was built
--------------
The comment section at the bottom of every recipe: read comments (paginated,
newest first), post one, edit or delete your own, like/dislike, and, if
you own the recipe, delete anyone's comment on it. It also adds a
reusable "Are you sure?" dialog, which Task 7 uses for deleting recipes.

How it was done
---------------
1. The moderation rule. The backend enforces who may do what, and the UI
   mirrors it so people only see buttons they're allowed to press:
     - Edit:   only the comment's author.
     - Delete: the author, OR the owner of the recipe ("my recipe, my
               comment section"). Imported Spoonacular recipes have no
               owner, so only authors can delete there.
   In code (src/features/recipe/CommentsSection.tsx):

     const isAuthor  = profile?.id === comment.user.id;
     const canDelete = isAuthor ||
                       (recipeOwnerId !== null && profile?.id === recipeOwnerId);

   `profile?.id` uses optional chaining: for an anonymous visitor profile is
   null, the expression is undefined, and both checks are false, so no
   buttons are shown. The `recipeOwnerId !== null` guard stops an anonymous
   visitor (undefined) from "matching" an ownerless recipe (null).
   RecipeDetailPage passes `recipeOwnerId={recipe.user?.id ?? null}`.

   Hiding buttons is a convenience, not security. The real check happens
   on the server (CommentService in the backend), so even a hand-crafted
   request can't delete someone else's comment.

2. Data: one useQuery for the current page of comments
   (queryKey ['comments', recipeId, page]) and three useMutation hooks
   (post / save edit / delete). Every successful mutation calls
   invalidate(), which refetches the comments and the recipe itself (its
   comment count changed). Failures call
     toast.error(e instanceof ApiError ? e.detail : 'Something went wrong')
   so the server's own message ("Only the author can edit a comment")
   shows in a toast.

3. Editing happens in place. Local state `editingId` remembers which
   comment is being edited. That comment's text swaps to an input
   pre-filled with the current body, with Save / Cancel buttons. Only one
   comment can be in edit mode at a time.

4. Reactions (the ReactionButtons component inside CommentsSection).
   The backend can toggle your reaction (PUT .../reactions/me {isLike},
   DELETE .../reactions/me), but it has no endpoint that says what your
   current reaction is. So the component remembers the reaction you made
   in this session:

     const [mine, setMine] = useState<boolean | null>(null);
     onClick={() => (mine === isLike ? unreact.mutate() : react.mutate(isLike))}

   Click 👍 once to like (PUT); click it again to remove it (DELETE).
   Clicking 👎 while liked switches it, since the backend upserts the same
   row. The counts come from the server, refetched after each change.
   Buttons are disabled for anonymous visitors. The trade-off: after a page
   reload, a thumb you'd pressed before doesn't show as highlighted. Fixing
   that would need a new backend endpoint.

5. src/components/ConfirmDialog.tsx — built on Radix UI's Dialog primitive
   rather than hand-written, because accessible modals are hard to get
   right. Radix moves keyboard focus into the dialog, traps Tab inside it,
   closes on Escape, and links Dialog.Title / Dialog.Description to the
   dialog for screen readers. Our part is the styling (square, black-bordered
   box over a 40% black overlay) and the props:
     ConfirmDialog({ open, title, description, confirmLabel,
                     onConfirm, onCancel })
   It's "controlled": the parent owns `open`. CommentsSection keeps
   `deletingId`; clicking Delete sets it (dialog opens) and Confirm runs the
   delete mutation, whose success clears it (dialog closes).

 TASK 7 — Recipe authoring form + owner edit/delete
 Commit on feature/frontend-pages: 57da9ac
================================================================================

What was built
--------------
One form page used for both creating (/recipes/new) and editing
(/recipes/:id/edit) a recipe. It has dynamic ingredient and step rows,
validation that runs before anything is sent, and server errors shown next
to the right field. On the detail page, the recipe's owner now sees Edit
and Delete buttons.

How it was done
---------------
1. One page, two modes (src/features/authoring/RecipeFormPage.tsx):

     const { id } = useParams<{ id: string }>();   // only present when editing
     const existing = useQuery({ queryKey: ['recipe', id],
                                 queryFn: () => getRecipe(id!),
                                 enabled: !!id });

   On /recipes/new there's no :id, so `enabled: !!id` is false and nothing
   loads. On /recipes/:id/edit the recipe is fetched. It reuses the same
   ['recipe', id] cache entry as the detail page, so coming from the detail
   page the data is already there. On submit:
     const saved = id ? await updateRecipe(id, dto) : await createRecipe(dto);
     navigate(`/recipes/${saved.id}`);

2. Validation with zod. A zod schema describes what a valid form looks like,
   with the same limits the backend enforces (title 1–255 chars, ingredient
   name ≤255, original text ≤500, instructions ≤50000, at least one
   ingredient, at most 100 ingredients/steps, at most 10 cuisines):

     ingredients: z.array(z.object({
         ingredientName: z.string().min(1, 'Name required').max(255),
         originalText:   z.string().min(1, 'Text required').max(500),
       })).min(1, 'At least one ingredient').max(100),

   `type FormValues = z.infer<typeof schema>` derives the TypeScript type
   from the schema, so the validation rules and the type can't drift apart.
   react-hook-form runs the schema through `zodResolver(schema)`: if
   anything fails, submit is blocked and each message lands under its field
   (role="alert", so screen readers announce it). Mirroring the backend's
   limits gives instant feedback without a server round-trip, and the
   server still re-validates everything.

3. Why numbers are strings in the form. HTML inputs always produce strings,
   and an empty box needs to mean "not set". So servings and the minute
   fields are strings in the form, converted only when building the request:
     const toInt  = (s: string) => (s.trim() === '' ? null : Number(s));
     const toNull = (s: string) => (s.trim() === '' ? null : s);
   An empty box becomes null, which the backend stores as "unknown".

4. toDto() turns form values into the exact JSON the backend expects
   (RecipeCreate). Steps become numbered InstructionStep objects:
     v.steps.map((s, i) => ({ number: i + 1, step: s.text,
                              ingredients: [], equipment: [] }))
   Numbering is derived from row order at submit time, so deleting a middle
   step can never leave a gap.

5. Dynamic rows with useFieldArray. react-hook-form's useFieldArray manages
   the ingredient and step lists: fields to render, append() for the "Add
   ingredient" button, remove(i) for each ✕. Each row is registered as
   `ingredients.${i}.ingredientName`, a dotted path into the form state.
   The ✕ is disabled while only one ingredient row remains, since at least
   one is required. Inputs carry aria-labels like "Ingredient 2 name" so
   each row is distinguishable for screen readers and tests.

6. Server errors onto fields. If the backend rejects the save with
   ProblemDetail { errors: { title: 'must not be blank' } }, the catch block
   loops over the errors and calls react-hook-form's setError(field,
   {message}), so the server's message appears under the same input as
   client-side errors would. Errors that aren't field-specific show as a
   toast instead.

7. Edit pre-fill. When the recipe arrives, a useEffect calls reset(...) with
   the recipe converted back into form shape: numbers to strings, null to
   '', steps to {text}. An existing recipe with zero ingredients still gets
   one empty row.

8. Image preview. `watch('image')` re-renders as you type the URL, and an
   <img> shows a live preview.

9. Owner actions on the detail page (RecipeDetailPage.tsx):
     {profile && recipe.user?.id === profile.id && ( ...Edit link,
       Delete button, ConfirmDialog... )}
   Shown only when you're logged in AND the recipe's author is you.
   Imported recipes (user = null) never show them. Delete goes through the
   ConfirmDialog from Task 6, then a mutation calls DELETE /api/recipes/:id
   and navigates home. The backend's ownership check is the real protection.

   A React rule shaped where this code went: hooks (useAuth, useState,
   useMutation, useNavigate) must run in the same order on every render, so
   they sit at the top of the component, before the early returns for
   "loading" and "not found". A hook placed after an early return would
   only run on some renders, which React forbids.

 BUG FIX — Cuisine filter returned a server error (backend)
 Commit on main: see "fix: cuisine filter" below
================================================================================

Symptom
-------
Choosing a cuisine on the browse page showed "Couldn't load recipes". Every
other filter worked. The frontend tests hadn't caught it because they fake
the backend with MSW, so the real database query never ran in them.

How it was tracked down
-----------------------
1. Reproduced against the running backend: /api/recipes?vegan=true answered
   200, while /api/recipes?cuisine=italian answered 500 (server error). So
   the frontend was sending the right request, and the crash was in the
   backend.
2. Read the backend's filter code (RecipeSpecifications.java). The cuisine
   filter used Hibernate's built-in array_contains() function on the
   recipes.cuisines column, a Postgres text[] (array of text).
3. Decompiled Hibernate 7.4.1's array_contains implementation (from the
   local Maven cache) to see the SQL it generates:
     cuisines @> cast(array[?] as <the column's Hibernate type>)
   The entity maps cuisines as List<String>, which Hibernate treats as an
   array of varchar, not text.
4. Ran that exact SQL straight against the database (read-only, over JDBC):
     cast(... as varchar array) -> ERROR: operator does not exist:
                                   text[] @> character varying[]
     cast(... as text array)    -> OK, 40 recipes
   That proved the root cause: Postgres won't compare a text[] column with
   a varchar[] value, and Hibernate always cast the value to varchar[].

The fix
-------
A small custom Hibernate SQL function,
RecipeAppBackend/.../specification/TextArrayFunctions.java:

  registerPattern("text_array_contains",
                  "(?1 @> cast(array[?2] as text[]))", <boolean type>);

?1 and ?2 are placeholders for the function's arguments: the column and
the cuisine. Casting the value to text[] means both sides of @> have the
same type. @> is also the operator the GIN index on cuisines supports, so
the query stays index-friendly. Hibernate discovers the function through a
one-line registration file,
src/main/resources/META-INF/services/org.hibernate.boot.model.FunctionContributor,
which is Java's standard plug-in mechanism. RecipeSpecifications now calls
text_array_contains instead of array_contains.

No database or schema change was needed.

How it was tested
-----------------
  - TextArrayFunctionsTest (2 tests): the function registers, and Hibernate
    can actually discover it via the registration file. Forgetting that
    file would bring the 500 back silently. Both failed first (the class
    didn't exist yet).
  - All 66 existing backend tests still pass (68 total).
  - End to end on the running backend: cuisine=italian -> 200 with 40
    recipes, cuisine=mexican -> 200 with 40, cuisine+vegan combined -> 200.

Why this round happened
-----------------------
After v1 shipped, four things felt wrong:
  1. The filters sat in a cramped bar above the recipe grid.
  2. Cuisines were one long flat list with no way to browse by part of the
     world (Asia, Mediterranean, ...).
  3. Max time and min rating were fixed dropdown choices and couldn't be
     typed.
  4. The look was plain.

The redesign does four things:
  - It moves every filter into a slide-in drawer.
  - It groups cuisines by region, shows a "popular ten", and adds an A-Z
    page.
  - It restyles the whole app in a warm palette called "Golden Hour", with
    no emojis anywhere.
  - It makes the cuisine list a fixed, curated catalogue that the server
    checks.

Why a curated list, and not free text? If anyone could type any cuisine
name, trolls could invent joke cuisines and they would show up as filters
for everyone. A fixed list of every country plus a few regional styles
(Cajun, Southern, Nordic, ...) covers real dishes and can't be vandalised.

The order of the work: the backend first (Tasks 1-6), then the visual
foundation (7-8), then the filter plumbing (9), the recipe-form picker (11),

 REDESIGN TASK 1 — The cuisine catalogue (backend)
 Files: RecipeAppBackend/src/main/resources/cuisines.csv
        RecipeAppBackend/.../cuisine/{Region, CuisineEntry, CuisineCatalog,
                                      InvalidCuisineException}.java
================================================================================

What was done
-------------
A spreadsheet-style file, cuisines.csv, lists all 198 allowed cuisines:

  key,label,region,mediterranean
  albanian,Albanian,europe,true
  austrian,Austrian,europe,false
  ...

  - key    the lowercase value stored in the database and used in URLs.
  - label  what people see.
  - region one of europe, asia, americas, africa, middle_east, oceania.
  - mediterranean  a separate true/false flag. "Mediterranean" cuts across
           regions: Greece is in Europe, Lebanon in the Middle East and
           Morocco in Africa, and all three are Mediterranean.

How it works
------------
CuisineCatalog is a Spring @Component. Its constructor reads the CSV once at
startup and builds a lookup map from key to entry. It fails loudly (the app
refuses to start) on:
  - a missing file,
  - a row without exactly 4 fields,
  - an unknown region,
  - a duplicate key.
A typo in the list is caught on the first run instead of turning into a
silent bug.

The important methods:

  normalize(raw)
      raw.toLowerCase(Locale.ROOT).replaceAll("[\\s\\p{Z}]+", " ").trim()
    Turns "  ITALIAN " into "italian". [\s\p{Z}] matches every kind of
    whitespace, including the non-breaking space you get when copy-pasting
    from a web page (plain \s misses that one; a reviewer caught it).
    Locale.ROOT avoids the "Turkish i" problem, where lowercasing "I" on a
    Turkish-locale machine gives a dotless i.

  keysForRegion("asia")
    Every cuisine key in that region. "mediterranean" is special-cased to
    use the flag instead of the region column.

  resolveFilter(cuisines, regions) -> Optional<Set<String>>
    Turns the browse request's ?cuisine= and ?region= values into one set
    of keys. The return type carries three different meanings:
      Optional.empty()      no cuisine filter at all (show everything)
      Optional.of({})       a filter was asked for but nothing valid
                            matched, e.g. ?cuisine=lol, so show NOTHING
      Optional.of({a,b,c})  show recipes having any of these keys
    That middle case is the main reason for the design. A naive version
    would ignore the unknown value and return every recipe. That would be
    confusing ("I asked for X and got everything"), so the empty set is
    kept separate from "no filter".

  normalizeAndValidate(list)
    Used when saving a recipe. It normalises each entry, removes duplicates
    while keeping order (a LinkedHashSet), and throws
    InvalidCuisineException listing every unknown value.

How it was tested
-----------------
CuisineCatalogTest covers:
  - loading,
  - normalisation (tabs, newlines, the non-breaking space),
  - region and Mediterranean lookups,
  - all three resolveFilter outcomes,
  - de-duplication and the unknown-value error.

 REDESIGN TASK 2 — Multi-value cuisine and region filtering (backend)

================================================================================

What was done
-------------
RecipeFilter's single `String cuisine` became `List<String> cuisine` plus
`List<String> region`. Spring binds repeated query parameters
(?cuisine=thai&cuisine=greek) straight into a List.

How it works
------------
RecipeService.browse() first asks the catalogue to resolve the filter. If
the answer is "an empty set", it returns Page.empty() right away and never
touches the database. Otherwise it builds the query:

  Predicate[] anyOf = keys.stream()
      .map(key -> cb.isTrue(cb.function(TEXT_ARRAY_CONTAINS, Boolean.class,
                                        root.get("cuisines"), cb.literal(key))))
      .toArray(Predicate[]::new);
  predicates.add(cb.or(anyOf));

In SQL terms that is:

  (cuisines @> '{thai}' OR cuisines @> '{greek}')
      AND vegan = true AND ...

The cuisine part is an OR (any of the picked cuisines). It is ANDed with the
diet, time and rating filters. text_array_contains is the custom Hibernate
function from the earlier bug fix (see "BUG FIX — Cuisine filter returned a
server error" above). It keeps the query on the GIN index.

A region plus an explicit cuisine together form a union.
?region=asia&cuisine=italian gives every Asian recipe plus the Italian ones.
That is what a person ticking both would expect.

    repository.

 REDESIGN TASK 3 — GET /api/recipes/cuisines (backend)
 Files: repository/RecipeRepository.java (countCuisines),
        model/projection/CuisineCount.java, model/displayDTO/CuisineInfoDto.java,
        service/CuisineService.java, controller/CuisineController.java
================================================================================

What was done
-------------
A new public endpoint returns every catalogue cuisine with how many recipes
use it:

  [{"key":"italian","label":"Italian","region":"europe",
    "mediterranean":true,"count":12}, ...]

How it works
------------
Counting uses one native SQL query:

  select c as key, count(*) as count
  from recipes, unnest(cuisines) c
  group by c

unnest() turns each recipe's array into one row per cuisine, so a simple
GROUP BY counts them. CuisineCount is a Spring Data "projection": an
interface with getKey() and getCount() that Spring fills from the result
columns.

CuisineService then walks the WHOLE catalogue and gives each cuisine its
count, or 0 if no recipe uses it. It sorts by count (highest first), then by
label. The frontend relies on that order: the "popular ten" is simply the
first ten entries with a count above zero.

Routing detail
--------------
/api/recipes/{id} already existed. The new mapping is the literal path
/api/recipes/cuisines, and Spring prefers a literal path over a {variable}
one, so "cuisines" is never read as a recipe id. The security config keeps
the endpoint public, so anonymous visitors can browse. A test covers both.

Live check: on the running backend the endpoint returned 200 with 198
entries and real counts.

 POLISH — Pointer cursor on every clickable control (frontend)
 Branch: fix/pointer-cursors   File: src/index.css
================================================================================

Symptom
-------
Hovering over many clickable things showed the plain arrow cursor, not the
pointing hand: the rating stars, like/dislike, comment edit/delete, the
filter chips in the drawer, and pagination.

Cause
-----
Tailwind v4's CSS reset ("preflight") deliberately changed buttons back to
the browser default cursor (an arrow). Tailwind v3 had used the hand. Links
(<a>) were unaffected, which is why cards and nav links still showed the
hand. Every control above is a real <button>, so they all lost it at once.

Fix
---
One rule in the base layer of index.css, the approach Tailwind's own v4
upgrade guide recommends:

  button:not(:disabled),
  [role='button']:not([aria-disabled='true']),
  select:not(:disabled) {
    cursor: pointer;
  }
  button:disabled,
  select:disabled {
    cursor: not-allowed;
  }

Why one global rule rather than adding cursor-pointer to each button: there
are about 30 buttons across the app, and any new one would forget it again.

Disabled buttons show the "not allowed" cursor, for example:
  - like/dislike when you are signed out,
  - "Previous page" on page 1,
  - "Clear all" when no filter is set.
Number inputs keep the text cursor, because you type in them.

Why it doesn't fight existing classes: @layer base has the lowest priority
in Tailwind. Any utility class on an element, such as cursor-pointer or
disabled:cursor-not-allowed, still wins over this rule.

How it was checked
------------------
  - In the running app, the browser's computed style showed `pointer` on
    Filters, the pagination buttons, the drawer close button, every region,
    cuisine and dish-type chip, the 15/30/60 quick picks and "Show N
    recipes". It showed `not-allowed` on the disabled "Previous page" and
    "Clear all", and `text` on the number inputs.
  - Tests: 73/73 still pass, and the build is clean.

 BUG FIX — Like/dislike highlight forgotten after leaving a recipe
 Branch: fix/remember-comment-reactions
================================================================================

Symptom
-------
You like a comment and the thumb lights up. You open another recipe and
come back, and the thumb is no longer highlighted, even though the like is
still saved (the count still includes it).

Root cause
----------
The highlight lived only in the component's memory:

  const [mine, setMine] = useState<boolean | null>(null);

React throws component state away when the component leaves the screen
("unmounts"). Opening another recipe unmounts the comments, so coming back
started again from null. The original code said why in a comment: the API
had no way to read "my reaction" back, so the frontend could only remember
clicks made during the current visit.

The star rating never had this bug, because it has
GET /api/recipes/{id}/ratings/me. Comment reactions had no equivalent.

The fix, backend
----------------
New endpoint:

  GET /api/recipes/{recipeId}/comments/reactions/me
  -> { "<commentId>": true, "<otherCommentId>": false }

  - true means liked and false means disliked. Comments you haven't
    reacted to are simply absent.
  - One call covers every comment on the recipe, so a page of 10 comments
    costs 1 request, not 10.
  - It is backed by one JPQL query, which builds a small record
    (MyCommentReaction) per row:

    SELECT new ...MyCommentReaction(r.comment.id, r.isLike)
    FROM CommentReaction r
    WHERE r.comment.recipe.id = :recipeId AND r.user.id = :userId

  - It needs a signed-in user. The @CurrentUserId parameter answers 401
    to anonymous callers.
  - SecurityConfig was not touched: the path already falls under the
    public GET rule, and the 401 comes from the parameter resolver.

The fix, frontend
-----------------
  - api/reactions.ts gained getMyReactions(recipeId).
  - CommentsSection loads it once per recipe with TanStack Query. The cache
    key includes the user id, so switching accounts never shows someone
    else's highlights:

      queryKey: ['myReactions', recipeId, profile?.id]
      enabled:  status === 'ready'      (only when signed in)

  - ReactionButtons no longer keeps its own state. It gets
    `mine = myReactions.data?.[comment.id] ?? null` from its parent. After
    a like, dislike or removal succeeds, it updates that cached map
    directly with queryClient.setQueryData, so the highlight changes at
    once without waiting for a refetch.
  - The buttons are disabled for the moment it takes the saved reactions
    to load. Otherwise a fast click on an already-liked thumb would send
    "like" again instead of removing the like. The rating stars wait the
    same way.
  - The buttons now carry aria-pressed. Screen readers announce
    "pressed", and tests can check the highlight.

How it was tested
-----------------
  - Backend:
      - CommentControllerTest: the signed-in user gets the map; anonymous
        gets 401 and the service is never called.
      - New CommentReactionQueryDbTest (read-only, real Postgres): every
        stored reaction is found for its own user and recipe, and an
        unknown user gets nothing.
  - Frontend: a new test loads a recipe where the server says comment c-1
    is liked. It checks that the Like button shows as pressed, that
    clicking it sends DELETE (not PUT), and that the highlight clears. The
    test failed before the fix.
  - Totals: 74/74 frontend tests, build clean. On the running backend the
    new endpoint answers 401 to anonymous callers.

Side note: two DB tests must share one config
---------------------------------------------
The first version of the new DB test also set ddl-auto=validate. Because
its settings differed from RecipeCuisineQueryDbTest, Spring built a second
test context with its own pool of database connections. Together with the
running backend, that hit Supabase's session-mode limit of 15 clients
("EMAXCONNSESSION"). Giving both tests identical settings lets Spring reuse
one cached context. application.properties already sets validate, so
nothing was lost.

 PART 3 — PHOTO COLLAGE
 Branch: feature/photo-collage

Why this round happened
-----------------------
Two things felt wrong with recipe images:
  1. A recipe could only have one picture, and it was a pasted web link.
     People wanted several photos of a dish, shown together as a collage.
  2. The recipe form asked for "Source name" and "Source URL". Those make
     sense for recipes imported from elsewhere, but not for a recipe somebody
     writes on Plateful, so they confused people.

The decisions taken before any code was written:
  - Photos come from the user's own device. There is no "paste an image
    link" any more (uploads only).
  - At most 6 photos per recipe.
  - The first photo is the cover. It is what the recipe cards and the top of
    the recipe page show. Reordering the photos changes the cover.
  - The browser uploads straight to Supabase Storage, not through our
    backend. The backend never handles image bytes. It only stores and checks
    the file paths.
  - The form no longer has Image URL, Source name or Source URL. The server
    also stops reading those three fields from a request, so an old client
    that still sends them is harmlessly ignored.

The order of the work: the database and storage rules (Task 1), the backend
path checking (2), the backend create/update/read (3), the frontend upload
helpers (4), the picker (5), the recipe form (6), and finally the collage on
the recipe page (7). Task 8 is this write-up plus the final check.

What was done
-------------
A new table, recipe_photos, holds one row per photo: the recipe it belongs
to, the storage path, and a position (0 is the cover). A UNIQUE constraint on
(recipe_id, position) means two photos can never claim the same slot.

The Flyway migration V3 creates this table. The storage bucket is not part of
Flyway (Flyway only owns the public schema), so it lives in a separate script,
docs/supabase/recipe-photos-storage.sql, that is run once by hand in the
Supabase dashboard.

How the storage rules work
--------------------------
The script creates a public bucket called recipe-photos (anyone can view the
images, so no read rule is needed) limited to 5 MB per file and to JPEG, PNG
and WebP. Then it adds two rules on storage.objects, both for signed-in
users only:

  with check (
      bucket_id = 'recipe-photos'
      and (storage.foldername(name))[1] = auth.uid()::text
  )

  - A user may upload (insert) a file only if the first folder in the path is
    their own user id. Path: {userId}/{uuid}.{ext}.
  - A user may delete a file only from their own folder, by the same test.
  - There is deliberately no UPDATE rule. Files are never overwritten: a
    changed photo is a new file with a new random name.
The script can be run twice safely: the bucket insert does nothing if the
bucket exists, and each rule is dropped before it is created again.

The entity and the SMALLINT mapping
-----------------------------------
The position column is SMALLINT (it only ever holds 0 to 5). But the Java
field is an Integer, and the backend runs Hibernate with
ddl-auto=validate, which compares the Java type with the real column type at
startup. Integer against SMALLINT fails with "found smallint, expected
integer" (the same trouble V2 had to fix for older columns). The fix is one
annotation on the field:

  @JdbcTypeCode(SqlTypes.SMALLINT)
  private Integer position;

It tells Hibernate "this Integer is stored as a smallint", and validation
passes.

Why there is a bulk delete
--------------------------
When a recipe's photos are replaced, the old rows must go before the new ones
go in. The obvious way, deleting the old entities with a derived delete and
then saving new ones, breaks. Hibernate flushes inserts before deletes. So
the new row at position 0 would be written while the old row at position 0
still exists, and the UNIQUE (recipe_id, position) constraint rejects it.
The repository therefore uses one explicit JPQL delete query:

  @Modifying(flushAutomatically = true)
  @Query("delete from RecipePhoto p where p.recipe.id = :recipeId")
  void deleteAllByRecipeId(UUID recipeId);

It runs immediately as a single SQL DELETE, so the table is empty for that
recipe before the inserts. (flushAutomatically makes Hibernate write any
pending changes first. Task 3 deliberately does NOT clear the persistence
context after the delete: clearing would detach the recipe in the middle of
an update and break the rest of it.)

The repository also has two read methods: photos of one recipe in position
order, and photos of many recipes at once (used by the list pages, Task 3).

How it was tested
-----------------
RecipePhotoRepositoryDbTest runs against the real database inside a
transaction that is rolled back, so no rows are left behind. One test does a
replace (bulk delete, then insert at the same positions) and checks the order
and that nothing violates the UNIQUE constraint. The other checks that the
batched read groups photos by recipe. 2 tests.

 PHOTO TASK 2 — Checking photo paths (backend)
 Files: .../photo/RecipePhotoPaths.java, InvalidPhotoException.java,
        .../exception/GlobalExceptionHandler.java (handleInvalidPhoto)
        application.properties (one line)
================================================================================

What was done
-------------
The server never sees the image. It receives a list of storage paths in the
recipe request, so it has to make sure those paths are legitimate. A user must
not be able to attach somebody else's file to their recipe, or point a recipe
at some outside web address.

How it works
------------
RecipePhotoPaths.validate(callerId, paths) applies these rules, in order:
  - null counts as an empty list;
  - more than 6 paths: "At most 6 photos";
  - every path must match this pattern, built fresh for the caller:

      ^{callerId}/[0-9a-fA-F-]{36}\.(jpg|png|webp)$

    otherwise "Invalid photo: <path>";
  - the same path twice: "Duplicate photo: <path>".

Why the pattern blocks what it should:
  - The caller's own id is the literal start of the pattern, so
    {someoneElse}/... never matches. That blocks other users' files. This
    mirrors the storage rule: you can only add to your own folder.
  - The path must be exactly id, slash, 36 characters of hex and dashes (a
    UUID's shape), a dot, and one of three extensions, all anchored from start
    to end. A full web address (https://...) starts with the wrong characters,
    so it can't match. "../" tricks and extra folders can't match either.
  - The caller's id is wrapped in Pattern.quote so it is matched as plain text.

A failure becomes an HTTP 400 with the same shape as the cuisine errors:
detail "Validation failed" and errors = {"photos": "<message>"}.

The public base URL of the bucket comes from one property in
application.properties (app.storage.photos-public-base-url).
publicUrl(path) is that base, a slash, and the path. One line moved from the
next task to this one, because the validation class needs the property and the
auto-restarting backend would otherwise have failed to start in between.

How it was tested
-----------------
RecipePhotoPathsTest (10 tests): good paths kept in order, null, another user's
folder, "../" tricks, full URLs, wrong extensions, a missing UUID-style name,
duplicates, seven paths, and the URL builder. A test in
GlobalExceptionHandlerTest checks the 400 body.

 PHOTO TASK 3 — Photos in create, update and read (backend)
 Files: .../service/RecipeService.java, .../model/createDTO/RecipeCreateDto.java,
        .../model/displayDTO/RecipeDisplayDto.java
================================================================================

What was done
-------------
  - RecipeCreateDto lost image, sourceName and sourceUrl, and gained
    photos (a list of at most 6 paths). Because Jackson ignores unknown JSON
    properties, a client that still sends the old fields is silently ignored.
    Nothing a user sends can set those three fields any more.
  - RecipeDisplayDto gained photos, a list of full public URLs in order.

Create
------
The photos are validated first. The recipe's own "image" column is set to the
cover's URL (or left empty with no photos), the recipe is saved, and one
recipe_photos row is written per path at positions 0, 1, 2, ... Keeping image
filled means every older place that reads "image" (recipe cards, imports)
keeps working without knowing about the new table.

Update
------
  1. Owner check first. Somebody else's recipe gives the normal "not yours"
     answer before any photo is looked at.
  2. Cuisines and photos are validated. A rejected photo list changes
     nothing.
  3. The old rows are removed with the bulk delete, the new rows saved, and
     image set to the new cover (or cleared).

The legacy linked-image rule: recipes made before this feature, and the
imported Spoonacular ones, have an image link but no photo rows. If an edit
arrives with an empty photo list and the recipe has no photo rows, the update
does nothing to the image. It would otherwise wipe the old picture just because
the person fixed a typo in the title. Once the person adds a photo, the rows
and the new cover replace it. In code:

  if (photos.isEmpty() && !photoRepository.existsByRecipeId(recipeId)) {
      // legacy recipe: leave the image alone
  } else {
      photoRepository.deleteAllByRecipeId(recipeId);
      ... save new rows, set image to the cover or null
  }

Read
----
A recipe with photo rows returns their URLs in position order. A recipe with
no rows but an image link (a legacy or imported one) returns that link as a
one-item list, and a recipe with neither returns an empty list. So the
frontend only ever reads "photos".

The one batched photo query per page: the browse and search pages show up to
dozens of recipes. Asking the database for each recipe's photos separately
would be one query per card. The page assembly instead collects all recipe ids
and makes ONE query, findByRecipeIdInOrderByPositionAsc(ids), then groups the
rows by recipe in memory. That is one extra query per page, no matter how many
recipes are on it (the same approach already used for ingredients, ratings and
comment counts).

How it was tested
-----------------
RecipeServicePhotosTest (9 tests) covers create (cover and order, source fields left
empty, a foreign path rejected), update (replace, clearing, the legacy rule,
a non-owner refused before photos are checked), the fallback to the image link
for imported recipes, and the one-batch browse query. The existing
controller and service tests were updated for the new constructor and DTO
shapes. Controller test checks $.photos in the response. 118 targeted backend
tests plus the 5 real-database tests pass.

 PHOTO TASK 4 — Upload helpers and in-browser shrinking (frontend)
 Files: src/api/photos.ts, src/lib/resizeImage.ts, src/lib/types.ts
================================================================================

What was done
-------------
Two small modules, plus type changes (RecipeDisplay gets photos; RecipeCreate
loses image/sourceName/sourceUrl and gets photos).

src/api/photos.ts has the constants (bucket name, 6 photos, 5 MB, the three
accepted types) and four functions:
  - uploadPhoto(userId, blob, ext) sends the file straight to Supabase
    Storage at {userId}/{random uuid}.{ext}, with upsert false, so a name can
    never overwrite an existing file. It returns the path.
  - deletePhotos(paths) removes files. It is best effort: a failure is only
    logged, and it never breaks what the user was doing.
  - publicPhotoUrl(path) and pathFromPublicUrl(url) convert both ways. Both
    use one shared base, so they always round-trip. pathFromPublicUrl returns
    null for any address that is not in our bucket, which is how the form
    tells our photos from old linked images.

In-browser shrinking
--------------------
A phone photo is often 4000 pixels wide and several MB. Shrinking happens in
the browser before upload (src/lib/resizeImage.ts, prepareImage):
  - The longest side is scaled down to at most 2000 px (smaller images are not
    enlarged). The aspect ratio is kept.
  - It is re-encoded as WebP at quality 0.85.
  - Some browsers answer a WebP request with a PNG without saying so, so the
    code checks the type of the result. If it is not WebP (or is empty), it
    encodes again as JPEG at 0.85 and uses the .jpg extension.
  - If the image can't be read: "Couldn't read this image". If it is still
    over 5 MB after shrinking: "Photo is too large even after resizing".
This keeps uploads fast and well under the bucket's 5 MB limit.

How it was tested
-----------------
17 tests across resizeImage.test.ts and photos.test.ts (sizes, the WebP then
JPEG fallback, the error messages, URL round-trips, upload and delete calls).
The decoding and drawing functions are injected in tests, because the test
environment (jsdom) has no real canvas; the real canvas path is therefore not
covered by the automated tests. Whole frontend suite then: 90 tests.

 PHOTO TASK 5 — The photo picker (frontend)

What the user sees
------------------
A "Photos" section in the recipe form with an "Add photos" button (it accepts
several files at once) and a grid of tiles. Each finished tile has:
  - "Move photo N left" and "Move photo N right" arrows (disabled at the

  - a remove button,
  - a "Cover" label on the first tile.

How it works
------------
Files are processed one at a time (shrink, then upload), so photos land in the
order they were chosen. As soon as a file is uploaded, its path is handed to
the form through onChange; the picker itself keeps only temporary tiles.

The busy state: the picker tells the form whether anything is uploading or
failed:

  onBusyChange(tiles.length > 0)

while a tile is pending or in an error state, the form's Save button stays
disabled (Task 6). So a recipe can't be saved with a photo missing because it
was still on its way up, or silently dropped after an error. Removing the
tile (or retrying successfully) clears the state.

Preview images use temporary browser URLs. They are released when a tile
finishes, is removed, or the picker closes, so memory isn't leaked. Removing
a pending tile makes the picker ignore its late result.

Why this round happened
-----------------------
Two requests from the user:
  1. A table of five seas (Mediterranean, Caribbean, North Sea, Sea of Japan
     & Pacific, Gulf of Mexico), each with a "vibe", its star ingredients and

  - Sorting is done by the database, over the whole result, not by the browser
    on the one page it happens to hold. Nothing new is stored on recipes: the
    rating and comment numbers are computed when needed.
  - The sort control is a native select, and the sea information is shown
    only for the seas that are ticked.

================================================================================
 SEA TASK 3 — Browse sort orders (backend)
 Files: .../model/RecipeSort.java, exception/InvalidSortException.java
        .../exception/GlobalExceptionHandler.java
        .../specification/RecipeSpecifications.java (withSort)
        .../service/RecipeService.java, controller/RecipeController.java
        .../repository/RecipeSortDbTest.java (new, real database)
================================================================================

What was done
-------------
Browse takes a new parameter, sortBy, with four values:
newest, most-rated, top-rated, most-comments. Missing means newest. An unknown
value is a 400 in the same shape as the other validation errors:
detail "Validation failed" and errors = {"sortBy": "Unknown sort: <value>"}.
The client no longer sends Spring's own "sort" parameter; if some client still
does, the server ignores it (the service builds a PageRequest with only the
page number and size).

The four ORDER BY rules
-----------------------
  newest         created_at desc, id asc
  most-rated     rating count desc, average rating desc (nulls last),
                 created_at desc, id asc
  top-rated      average rating desc (nulls last), rating count desc,
                 created_at desc, id asc
  most-comments  comment count desc, created_at desc, id asc

"Most popular" in the UI is top-rated: the best average first, and the number
of ratings breaks a tie (a 5.0 from many people beats a 5.0 from one).
Recipes nobody has rated have no average at all, so "nulls last" puts them at
the end instead of letting the database decide.

Every rule ends with id asc. If two recipes tie on everything else (same
rating numbers, same created_at), the database could return them in either
order, and the order could differ between the page-1 request and the page-2
request, so a recipe could show up on both pages or on neither. A last key
that is unique makes the whole order total, so paging is stable.

Correlated subqueries instead of stored columns
-----------------------------------------------
The rating count, rating average and comment count are computed with
subqueries, one per recipe row ("how many ratings does THIS recipe have"):

  ratingCountQ.where(cb.equal(rc.get("recipe"), root));

withSort(...) is a Specification that only sets query.orderBy(...) and adds no
condition, so it combines with the filter through and(). Nothing is added to
the recipes table, so there is nothing to keep in sync when someone rates or
comments. The cost is two or three small subqueries per row, which is fine at
this size; stored (denormalized) counts are the thing to revisit only if
sorting gets slow (the spec lists that as out of scope).

The count query and the Long guard
----------------------------------
A page of results needs a second query: "how many recipes match in total".
That one has no use for an ORDER BY (Spring clears it anyway). withSort checks
the result type of the query being built; if it is Long, it is the count
query, and the method returns early without building the subqueries:

  if (query == null || Long.class.equals(query.getResultType())) {
      return cb.conjunction();
  }

So the totals stay correct and no work is wasted.

Browse always uses the Specification
------------------------------------
Before, a browse with no filter took a shortcut (findAll(pageable)). That
shortcut had no way to apply a sort, so browse now ALWAYS goes through
findAll(filterSpec.and(sortSpec), page). With no filter the filter part just
matches everything. The short-circuit stays for "only unknown cuisines": that
still returns an empty page without asking the database.

How it was tested
-----------------
Unit tests: browse passes sortBy through, defaults to newest, an unknown
sortBy is 400, an empty filter still takes the Specification path, and the
PageRequest is unsorted but keeps the page number and size. A handler test
checks the 400 body.

RecipeSortDbTest runs against the real database (same annotations as the other
DB tests, see below). Five tests check that each order holds over the first
page: counts non-increasing, non-null averages before nulls, createdAt
non-increasing, and that two pages don't overlap. But the live database held
almost no recipes when this was written, so those checks hold trivially. A
sixth test therefore plants its own data: it inserts four recipes with ratings
and comments, borrows two existing users (read only), and asserts the exact
order of those four for each of the four sorts. The data distinguishes the
count-first rule from the average-first rule (two ratings averaging 3, against
one rating of 5, one of 4, and one recipe with no rating). It runs inside the
test's transaction, which is rolled back and never committed, so it leaves
nothing behind; if fewer than two users exist it skips.

Hibernate accepted ORDER BY over subqueries and Postgres executed them, so the
plan's "stop if Hibernate refuses" condition never came up.

A fixture fix for an older DB test: RecipePhotoRepositoryDbTest used the first
recipe in the table, which clashes with the UNIQUE (recipe_id, position) rule
when that recipe already has photos. It now picks a recipe without photo rows
and skips (not fails) if there is none.

Same annotations as the other DB tests
--------------------------------------
Every DB test class carries exactly the annotations of RecipeCuisineQueryDbTest,
including @TestPropertySource(properties = "spring.flyway.enabled=false").
Identical settings let Spring reuse one cached test context. A class with
different settings would build a second context with its own connection pool,
and together with the running backend that can hit Supabase's limit of 15
clients (the same trouble described in Part 3).

writeSort drops page
--------------------
Changing the order changes which recipe is first, so page 3 of the old order
means nothing in the new one (and might not even exist). Resetting to page 1
is the only sensible thing, so writeSort removes page from the address.

contained the whole address string, so a changed sort refetches without extra

Incident: imported recipes wiped
--------------------------------
During this round the imported (Spoonacular) recipes in the database
disappeared. What happened, in order:
  - The backend had been left running with two launch arguments from an
    earlier one-off import:
      --spoonacular.import.enabled=true
      --spoonacular.import.replace-existing=true
  - Spring DevTools restarts the application whenever compiled code changes,

    (every task of this round) started the backend with the import switched
    on, and the import ran again in replace mode.

    imported ones were gone, and the DB tests that need Italian and Greek
    recipes started to fail.

The fix: stop the backend process completely (removing the arguments from the
run configuration alone is not enough while the old process keeps running),
start it again without arguments, and re-import once, after the daily quota
resets.

Lesson: after any one-off import run, stop the process completely before
making code changes. A DevTools restart is not a fresh start with new
settings.

  - 13 or older: supabase.auth.signUp is called with
    options.data.age_confirmed_at (ISO time of the check). The birth date is not
    part of the request. The rest of the flow is unchanged.

  - The server does not check age_confirmed_at; it is only stored in the

 PART 6 — TWO-FACTOR AUTHENTICATION
 Branch: feature/two-factor-auth

################################################################################
################################################################################

Why
---
The user asked for two-factor authentication (2FA) and made four choices:
  - Optional: each user turns it on from their own profile page. Nobody is
    forced.
  - Server-enforced: it is not only a screen in the browser. For an account
    with 2FA, the backend itself refuses account and write actions unless the
    sign-in included a code. A password alone is not enough.
  - Up to 2 authenticator devices per account (a phone and a spare).
  - Recovery by hand: if a user loses every device, the site owner removes
    their factors with one SQL line (see Recovery below). There are no backup
    codes and no SMS.

The method is an authenticator app (Google Authenticator, Microsoft
Authenticator, Authy, a password manager) producing 6-digit codes that change
every 30 seconds (TOTP). It runs on Supabase Auth's built-in MFA, which is free.
Enrolling, challenging, verifying and removing a device all happen directly
between the browser and Supabase, using the user's own session. The backend
gained no endpoints and the database no migration; it only checks one thing
(see Task 1).

Spec: docs/superpowers/specs/2026-10-13-two-factor-auth-design.md
Plan: docs/superpowers/plans/2026-10-13-two-factor-auth.md
Work was done in six tasks (commits 2888751 to e2bd0cf), each reviewed.


Supabase assurance levels (AAL), in plain words
-----------------------------------------------
Every Supabase access token has an "aal" claim saying how strongly the person
proved who they are:
  - aal1: they entered the password (or used a magic link). One factor.
  - aal2: they also entered a valid code from their authenticator app.
After a code is verified, Supabase refreshes the session and the new token says
aal2. The browser library reports two levels, currentLevel and nextLevel. When
currentLevel is aal1 and nextLevel is aal2, the user HAS a verified device but
has not entered a code in this session yet. This log calls that "half signed
in". A user with no 2FA stays at aal1 for good (nextLevel is aal1 too) and is
treated as before.


Task 1 — Backend: cached lookup of verified factors
---------------------------------------------------
File: security/MfaFactorLookup (a @Component). Commit 2888751.
  - hasVerifiedFactor(UUID) runs exactly:
      select exists(select 1 from auth.mfa_factors
                    where user_id = ? and status = 'verified')
    Supabase keeps factors in auth.mfa_factors, and the backend's existing
    database connection can read it. It asks only "is there a verified one?".
    It never selects the secret column or any other column; a unit test checks
    that the SQL text contains no "secret".
  - Results are cached per user for 60 seconds (ConcurrentHashMap holding the
    answer and its expiry time, with an injectable Clock for tests). The cap is
    10,000 entries; when it is full the cache is cleared. No new dependency.
    Without the cache every write request would cost a query against the auth
    schema.
  - Cost of the cache: for up to 60 seconds after someone turns 2FA on, a half
    signed-in token may still pass. Accepted, because the person turning it on
    is the account owner. The same 60 seconds apply after a reset (Recovery).
  - Ruling: the Clock is not a bean. The public constructor takes only the
    JdbcTemplate and uses the system clock; a package-private constructor takes
    a Clock for tests. This avoids adding a global bean for one class.
  - Ruling (added in Task 2): a null result from the query throws instead of
    meaning "no factor", so the lookup is fail-closed as well. A failed lookup
    is never cached.
Tests: 5 unit tests at first (cache hit inside the TTL, re-query after it,
per-user cache, no secret in the SQL, clearing when full) and one
real-database test (a random user id has no factor), run against the live
Postgres. The "has a factor" path is not covered against the real database: the
test is read-only and there is no known fixture user.


Task 2 — Backend: the enforcement filter
----------------------------------------
Files: security/MfaEnforcementFilter, config/SecurityConfig. Commits c120d18 and
636c954 (fix).
Rule, in one place: for an authenticated request that needs an account (any
method other than GET, or a path ending in /me), whose token is not aal2, and
whose user has a verified factor, the filter answers by itself:
  - 401, header WWW-Authenticate: Bearer error="insufficient_user_authentication"
    (the standard "step-up" answer), and a ProblemDetail body with
    detail "Two-factor verification required" and code "mfa_required".
Everything else continues unchanged. Public GETs (browse, a recipe, comments,
profiles) are never blocked. Anonymous requests are untouched, so existing
behaviour holds. A token without an aal claim is treated as aal1. The paths
ending in /me cover /api/users/me, the user's own rating, and the user's own
reactions.

Fail-closed: if the lookup throws (database down, null result), the filter
answers 503 "Could not verify two-factor status". It never lets a request
through unchecked. The log line carries only the exception class name.

Why the filter must NOT be a bean: it is created with `new` inside
SecurityConfig and added with addFilterAfter(..., BearerTokenAuthenticationFilter).
A servlet Filter that is also a Spring bean is registered a second time by
Spring Boot as a plain servlet filter, so it would run twice per request, once
outside the security chain where there is no authentication yet. The class has
no @Component and a test (filterIsNotABean) fails if someone adds one.

The percent-encoded /me bypass (found in review). The first version tested the
raw request URI for the "/me" ending. The reviewer tried
GET /api/users/m%65 (%65 is the letter "e") with a half signed-in token: the
filter saw a path that did not end in /me and let the request through, but
Spring decodes the path before routing, so it reached the /me handler and
returned 200. The fix asks Spring's own UrlPathHelper for the decoded path
(also with ;matrix content removed) before the /me check. Three new tests send
the encoded form for the user, rating and reaction endpoints, and the first
one reproduced the bypass before the fix. The reviewer then probed %6D%65, a
context path, double encoding (%25), %2F and ;matrix variants: all are either
guarded or rejected earlier by Spring Security's request firewall.
Tests: 10 filter tests at first (every case in the spec plus a missing aal
claim and any-exception-is-503), 13 after the fix, and two more lookup tests.
The six @WebMvcTest controller tests that import SecurityConfig each got a
@MockitoBean MfaFactorLookup.


Task 3 — Frontend: the API client understands mfa_required
----------------------------------------------------------
File: src/api/client.ts. Commit 0abab0c.
Before this, the client called supabase.auth.signOut() on EVERY 401. With
enforcement on, a half signed-in user would be signed out the moment the backend
asked for a code, and could never reach the code step. Now:
  - ApiError has a new field, code, read from the problem body.
  - On a 401 whose body has code "mfa_required", the client does NOT sign out.
    It calls a registered handler (setMfaRequiredHandler) and throws an
    ApiError carrying the code.
  - Any other 401 still signs out, as before.
The handler is one module-level callback; AuthProvider registers it on mount
and clears it on unmount.


Task 4 — Frontend: the "needs-mfa" state, redirect and escape hatch
-------------------------------------------------------------------
Files: src/auth/aal.ts (new), AuthProvider, ProtectedRoute, AppShell,
AppRoutes. Commits e9fdcb9 and cee0052 (fix).
  - aal.ts reads the aal claim from the access token (base64url payload) and
    never throws; unreadable tokens give null.
  - AuthProvider has a new status, 'needs-mfa'. When a session arrives it asks
    Supabase for the assurance level first. If currentLevel is aal1 and
    nextLevel is aal2, the status becomes 'needs-mfa', the profile is not
    loaded, and /me is not called. If the level lookup itself fails, it falls
    back to the normal path.
  - The dedupe key is "userId:aal". AuthProvider ignores repeated events for
    the same user so it does not reload the profile needlessly. The old key
    was just the user id, which would have ignored the upgrade after a code is
    verified (same user, aal1 to aal2) and left the user stuck in 'needs-mfa'.
    With the new key the upgrade reloads the profile and the status becomes
    'ready'.
  - ProtectedRoute sends a 'needs-mfa' user to /verify-2fa and keeps the page
    they wanted in `from`.
  - AppShell shows a "Finish signing in" link and a "Sign out" button in that
    state, so a half signed-in user can always back out.
  - /verify-2fa first existed as a placeholder heading (so the redirect test
    had somewhere to land); Task 5 replaced it.

Two problems found in review and fixed:
  1. getMe and mfa_required. If /me answered 401 mfa_required (for example the
     token is aal1 and the backend's view of the account differs from what the
     level check said), the catch treated every error other than 404 as a
     transient failure and put the user in 'anonymous' while a session was
     live: the header said "Sign in" and the user was in limbo. Now an
     mfa_required answer from /me lands on 'needs-mfa', and the key is kept so
     duplicate events do not retry in a loop.
  2. The page unmounting on the upgrade. When a user is already on a protected
     page and verifies a code, the session goes aal1 to aal2 for the same
     user. AuthProvider set the status to 'loading' for the reload, and
     ProtectedRoute shows a spinner instead of its children while loading, so
     the page was unmounted in the middle of the verification. For the profile
     page that would have wiped its own state (the "Two-factor authentication
     is on" message and the device list) right after the user confirmed a
     code. A readyUserId tracker now skips 'loading' when the same user
     re-resolves: the status stays 'ready' and the profile refetches in the
     background. A different user or a first load still shows 'loading'. A
     test checks that the profile heading is the same DOM node through the
     upgrade.


Task 5 — Frontend: the code step at sign-in
-------------------------------------------
Files: src/features/auth/VerifyTwoFactorPage.tsx (new), LoginPage.tsx,
AppRoutes.tsx. Commit 57a5d6f.
  - Route /verify-2fa (public, so ProtectedRoute cannot bounce it). The page
    handles each status itself: loading shows a spinner, anonymous goes to
    /login, ready goes straight on to `from` (or "/"), needs-mfa shows the form.
  - Title "Two-factor verification", subtitle "Enter the 6-digit code from your
    authenticator app." Field "Code" with inputMode numeric, autoComplete
    one-time-code, maxLength 6, pattern \d{6}.
  - Per-device challenge. With two verified devices the page shows a "Which
    device?" radio choice (the first is selected) and sends the CHOSEN factor
    id: challenge({factorId}) then verify({factorId, challengeId, code}). Every
    device has its own secret, and a challenge belongs to one factor, so a code
    from device B does not work against device A. If the page always used the
    first factor, a user whose code came from the second phone would be told
    "That code didn't work" with no way out.
  - Wrong code: "That code didn't work. Check your app and try again." (a 422
    or any message containing "code"). Other errors, such as Supabase's own
    rate-limit message, are shown as returned.
  - A secondary "Sign out" button is always there. With no authenticator found
    the page says so and offers only Sign out.
  - LoginPage: after signInWithPassword succeeds it checks the level. Half

Recovery: a user lost every device
----------------------------------
Use this ONLY when a user can no longer produce a code from any of their
devices (lost or reset phone, no spare device). Check that the request really
comes from the account owner first. In the Supabase dashboard, open the SQL
editor and run:

    delete from auth.mfa_factors where user_id = '<the user id>';

The user id is shown in Authentication -> Users. After that the user can sign
in with their password alone and set up 2FA again from their profile page. The
backend stops asking for a code within 60 seconds, because that is the lookup
cache time. Do not remove factors for a user who still has a working device:
they can remove it themselves from the profile page.


Rollout
-------
  1. In the Supabase dashboard check that Authentication -> Multi-Factor ->
     TOTP is enabled (it is on by default for new projects). If it is off,
     enrolling fails.
  2. No migration and no new environment variable. The backend reads
     auth.mfa_factors through its existing database connection.
  3. Deploy the backend and the frontend together. The client must understand
     "mfa_required" before the backend starts sending it: an old frontend would
     sign a 2FA user out on the first refused request, and the user could never

 PART 7 — INACTIVITY TIMEOUT
 Branch: feature/idle-timeout

################################################################################
################################################################################

What was done
-------------
A signed-in user who does nothing for 60 minutes is signed out. One minute
before that, a dialog asks "Still there?" with a live countdown. After the
sign-out the browser goes to /login, which shows "You were signed out after 60
minutes of inactivity." once. Frontend only; no backend change.

How it works
------------
  - src/auth/idleTimeout.ts holds the constants: IDLE_TIMEOUT_MS (60 min),
    WARNING_MS (60 s), ACTIVITY_THROTTLE_MS (5 s) and the two storage keys.
  - src/auth/useIdleTimeout.ts is the hook. Activity is pointerdown, keydown,
    touchstart, wheel and scroll (capture, passive) on window. At most one
    activity is recorded per 5 seconds; recording writes Date.now() to
    localStorage['plateful.lastActivity'] (in try/catch) and keeps a copy in
    memory.
  - Idle time is always "now minus the newer of the memory copy and
    localStorage", never a running counter. So activity in another tab (the
    'storage' event) resets this tab too, and a computer that slept is caught
    when the tab becomes visible again or the window gets focus: if the idle
    time is already 60 minutes or more, the user is signed out at once with no
    warning.
  - One setTimeout is re-armed to the next deadline: the start of the warning,
    then every second during the warning (never later than the deadline).
  - At the timeout: sessionStorage['plateful.signedOutIdle'] = '1' (try/catch),
    supabase.auth.signOut(), then navigate('/login'). A "fired" flag makes this
    happen once per idle period, even if the timer, focus and visibility checks
    run together. If signOut fails, the user is still sent to /login.
  - Only active while the auth status is ready, needs-mfa or needs-profile.
    When it becomes anonymous or loading (or the guard unmounts), timers and
    listeners are removed and the flag is reset. When a session starts, activity
    is recorded immediately, so an old timestamp from a previous session (for
    example 3 hours old) cannot cause an instant sign-out.
  - src/auth/IdleSessionGuard.tsx renders the dialog (Radix Dialog, same
    styling as ConfirmDialog): title "Still there?", body "You'll be signed out
    in N seconds due to inactivity.", buttons "Stay signed in" (records
    activity, closes) and "Sign out now" (signs out like a timeout). Any
    activity, Escape or a click outside also closes it and resets the clock.
    Opening the dialog is not activity. It is mounted once in AppShell, inside
    the router, so it can navigate.
  - LoginPage reads sessionStorage['plateful.signedOutIdle'] on mount, shows a
    role="status" panel (same style as "Check your email", Clock icon), and
    removes the key in an effect so it shows once.

Tests
-----
src/auth/idle-timeout.test.tsx (12), with fake timers and a mocked supabase
whose signOut fires SIGNED_OUT like the real client:
  - noSignOutWhileActive, warningAt59Minutes (60 s, then 50 s, no emoji),

The guard removes its listeners and timer on unmount, so it does not leak into
other tests.

Known limits
------------
  - The timeout is enforced in the browser only. A copied access token keeps
    working on the server until it expires; this is a convenience for shared
    computers, not a server-side session limit.
  - "Sign out now" also shows the "signed out after 60 minutes" message on the
    login page, because it signs out the same way as a timeout.
  - If localStorage is unavailable, only this tab's own activity is counted, so
    activity in another tab does not reset the clock.
  - The countdown text is not announced by screen readers on every second; the
    dialog itself is announced when it opens.
